Caso práctico · Ejercicio end-to-end
RecipeNow — App de Recetas por Suscripción (iOS & Android)
Una startup quiere lanzar una app de contenido de recetas en múltiples categorías: bebidas, parrilla, desayunos, ensaladas y postres. El modelo de negocio es freemium: 2 recetas gratuitas, luego paywall de suscripción. Los 3 componentes principales son un Feed de recetas, una carpeta de Guardados y un Buscador. Seguimos el ciclo AI-DLC completo desde la idea hasta el primer incidente en producción.
📱 iOS + Android (React Native) 👥 PM · CTO · iOS Dev · Android Dev · QA 💰 Freemium: 2 recetas gratis → suscripción ⏱ Inception: 3h · Bolt: 1–2 días c/u
Fase 1 · Inception
Mob Elaboration — 3 horas, equipo completo
La PM abre la sesión con el brief del producto. La IA lo convierte en estructura construible en tiempo real mientras el equipo valida cada pieza.

"Queremos una app de recetas para iOS y Android. El contenido está organizado en categorías: bebidas, parrilla, desayunos, ensaladas y postres. El negocio es por suscripción — los usuarios pueden ver 2 recetas sin pagar, después de eso les aparece el paywall. La app tiene tres secciones: un feed principal donde puedes explorar las recetas, una carpeta donde guardas las que te gustaron y un buscador. El contenido lo cargamos nosotros en un CMS."

🤖 IA propone — Intent Document
Objetivo de negocio: Crear una app de contenido de recetas que convierta usuarios gratuitos en suscriptores mediante una experiencia de descubrimiento de alto valor, limitando el acceso a 2 recetas sin suscripción.

Valor para el negocio: Monetización recurrente mediante suscripción mensual/anual. El contenido editorial (categorías curadas, calidad visual) es la ventaja competitiva.

Plataformas: iOS y Android — experiencia nativa en ambas a través de un stack compartido (React Native).

Modelo de acceso: Freemium con hard paywall. Las 2 recetas gratuitas son la muestra de valor antes de la conversión.

Fuera de alcance v1: Comentarios, ratings de usuarios, recetas generadas por usuarios, compartir en redes sociales.

Incorporado: el paywall no debe ser visible hasta que el usuario llegue a la receta 3 — sin candados en el feed. El contador de recetas gratuitas es por usuario (device ID si es anónimo, cuenta si está registrado).

Incorporado: arquitectura cliente-CMS directo (Contentful API). No hay backend propio en v1 — implica que toda la lógica de paywall y preferencias vive en el cliente + un servicio de autenticación/suscripción (RevenueCat para in-app purchases).
IA genera: User Stories
🤖 IA propone — User Stories
  • US-01
    Como usuario, quiero explorar un feed de recetas organizadas por categoría (bebidas, parrilla, desayunos, ensaladas, postres) para descubrir contenido relevante a mi interés.
    Criterio: el home muestra secciones horizontales por categoría · cada receta muestra foto, nombre, tiempo de preparación y nivel de dificultad · scroll infinito dentro de cada categoría
  • US-02
    Como usuario, quiero abrir una receta y ver todos sus pasos, ingredientes y foto, para poder cocinarla.
    Criterio: disponible sin cuenta para las primeras 2 recetas abiertas · contenido cargado desde Contentful · la pantalla funciona offline si la receta fue abierta antes
  • US-03
    Como usuario no suscrito, cuando intento abrir mi 3ª receta quiero ver una pantalla de suscripción clara que explique el beneficio y me permita comprar, para decidir si vale la pena.
    Criterio: el paywall aparece solo al intentar abrir la 3ª receta, nunca antes · muestra opciones mensual y anual · integrado con App Store y Google Play Billing vía RevenueCat
  • US-04
    Como suscriptor, quiero guardar recetas en una carpeta personal para acceder a ellas rápido sin buscarlas de nuevo.
    Criterio: botón de guardar en la receta y en el feed · las recetas guardadas persisten entre sesiones · se sincronizan en todos los dispositivos del mismo usuario
  • US-05
    Como usuario, quiero buscar recetas por nombre, ingrediente o categoría para encontrar lo que necesito sin scrollear.
    Criterio: resultados en <1 seg · búsqueda funciona offline sobre las recetas ya cargadas · las recetas bloqueadas para no suscritos aparecen en resultados pero muestran el paywall al abrirlas

Opciones: (a) Firebase Firestore — sin backend propio, reglas de seguridad client-side; (b) solo local (AsyncStorage) — no sincroniza, pero v1 simple. Decisión de arquitectura para Clarify en UoW-03 (Saved Folder). Por ahora el criterio de US-04 dice "persiste entre sesiones" — la sincronización cross-device se marca como stretch goal de v1.

02 · PLAN IA genera plan en 4 capas — el equipo lo ve formarse en vivo
🤖 Capa 1 — Functional Design
Flujo del Home: al abrir la app, se cargan las categorías disponibles → por cada categoría se carga la primera página de recetas (8 items) → la pantalla renderiza secciones horizontales scrolleables.

Flujo del Detalle: tap en una RecipeCard → RecipeDetailScreen → carga completa de la receta por slug → muestra imagen hero, info, ingredientes, pasos.

Estados de pantalla: Loading skeleton · Contenido · Error con retry · Vacío (categoría sin recetas).

Featured order: las recetas con featuredOrder aparecen primero en su categoría, ordenadas ascendente.
🤖 Capa 2 — NFR Design
Performance de imágenes: expo-image con caché automático en disco. Las fotos del feed se cargan en resolución reducida (400px); al abrir el detalle se carga la imagen full.

Scroll: FlashList en lugar de FlatList — 5–10× mejor rendimiento en listas largas.

Caché de datos: React Query con staleTime de 5 minutos. Si la receta está en caché y la red falla, se sirve del caché (offline básico).

Cold start: las categorías se precargan en background al iniciar la app para que el feed aparezca inmediatamente.
🤖 Capa 3 — Infrastructure + ADR
Stack: React Native + Expo SDK 50 · TypeScript · React Query (datos) · Expo Router (navegación) · FlashList (listas) · expo-image (imágenes)

Fuente de datos: Contentful Content Delivery API (GraphQL). El API key de Contentful vive en variables de entorno Expo — nunca en el código.

ADR-001: React Query vs Zustand para estado de servidor
Decisión: React Query. Razones: manejo automático de loading/error/cache/retry, invalidation sencilla para pull-to-refresh, compatible con el patrón offline de v1. Zustand se reserva para estado local de UI (e.g. categoría activa).

// RecipeCard.tsx
// Trazabilidad: US-01 · criterio: "muestra foto, nombre, tiempo, dificultad"

import { Image } from 'expo-image'
import { CATEGORY_COLORS, CATEGORY_PLACEHOLDERS } from '../config/categoryColors'

interface RecipeCardProps {
  recipe: RecipeCardData
  onPress: () => void
}

export function RecipeCard({ recipe, onPress }: RecipeCardProps) {
  const placeholderBg = CATEGORY_COLORS[recipe.category.slug] ?? '#E5E7EB'

  return (
    <Pressable style={styles.card} onPress={onPress}>
      <Image
        source={recipe.coverImage.url}
        style={styles.image}
        contentFit="cover"
        transition={200}
        // QA criterio: placeholder por categoría si imagen no carga en 8s
        cachePolicy="memory-disk"
        placeholder={{ uri: CATEGORY_PLACEHOLDERS[recipe.category.slug] }}
        onLoadStart={() => startTimer(8000, () => setShowOffline(true))}
      />
      <View style={styles.info}>
        <Text style={styles.title} numberOfLines={2}>{recipe.title}</Text>
        <View style={styles.meta}>
          <Text style={styles.time}>⏱ {recipe.prepTime} min</Text>
          <DifficultyBadge level={recipe.difficulty} />
        </View>
      </View>
    </Pressable>
  )
}

🤖 IA genera — Summary Report de UoW-01
Test results: 38/40 pasando
2 fallos: tests de snapshot de RecipeDetailScreen — la fuente "Playfair Display" no está disponible en el entorno de tests de Jest (solo en el simulador)

Trade-offs tomados:
— Se usa useInfiniteQuery con cursor en lugar de offset-based pagination: más complejo pero evita duplicados si el CMS actualiza el orden entre requests
